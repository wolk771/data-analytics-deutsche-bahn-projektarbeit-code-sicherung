Voranalyse: Vergleich von Dateiformaten mit Pandas¶

Ziel der Untersuchung¶

In dieser Voranalyse wird untersucht, wie sich verschiedene Dateiformate beim Speichern und Einlesen eines größeren Datensatzes verhalten.

Verglichen werden insbesondere:

  • Dateigröße,
  • Schreibdauer,
  • Lesedauer,
  • benötigter Speicherplatz und
  • praktische Eignung für die weitere Analyse.

Als Ausgangsbasis für diesen Performance-Test dient ein originaler Tabellen-Datensatz, der komprimiert im ZIP-Format vorliegt. In dem Format ist die Datei leicht über 100 MB groß.

Aber als pandas DataFrame wird fast 1 GB benötigen.

Die Untersuchung stellt zunächst einen Vergleich der verfügbaren Dateiformate mit Pandas dar. Die Ergebnisse bilden eine Grundlage für die spätere Auswahl geeigneter Dateiformate im Hauptprojekt.

Hinweis: Die gemessenen Zeiten können je nach Systemauslastung und Ausführungsbedingungen geringfügig variieren.

# Definition der Testvarianten - fastparquet ohne Levels
tests = [
    ("CSV", None, None, None, ".csv", {"index": False}),
    (
        "CSV_BZ2",
        None,
        None,
        None,
        ".csv.bz2",
        {"index": False, "compression": "bz2"},
    ),
    (
        "CSV_ZIP",
        None,
        None,
        None,
        ".csv.zip",
        {"index": False, "compression": "zip"},
    ),
    # Snappy-Vergleich
    ("Parquet", "pyarrow", "snappy", None, ".parquet", {}),
    ("Parquet", "fastparquet", "snappy", None, ".parquet", {}),
    # ZSTD-Vergleich (PyArrow mit echten Levels, fastparquet nur Standard)
    ("Parquet", "pyarrow", "zstd", 3, ".parquet", {}),
    ("Parquet", "pyarrow", "zstd", 10, ".parquet", {}),
    ("Parquet", "pyarrow", "zstd", 11, ".parquet", {}),
    ("Parquet", "fastparquet", "zstd", None, ".parquet", {}),
    # Brotli-Vergleich
    ("Parquet", "pyarrow", "brotli", 5, ".parquet", {}),
    ("Parquet", "pyarrow", "brotli", 10, ".parquet", {}),
    ("Parquet", "pyarrow", "brotli", 11, ".parquet", {}),
    ("Parquet", "fastparquet", "brotli", None, ".parquet", {}),
]

results = []

for fmt, engine, codec, level, ext, extra in tests:
    # Eindeutiger Dateiname für den Testlauf
    lvl_str = f"_lvl{level}" if level is not None else ""
    codec_str = f"_{codec}" if codec is not None else ""
    engine_str = f"_{engine}" if engine is not None else ""
    fname = f"bench_{fmt}{engine_str}{codec_str}{lvl_str}{ext}"

    kwargs = extra.copy()

    # --- SCHREIBEN ---
    start = time.time()
    try:
        if fmt.startswith("CSV"):
            df.to_csv(fname, **kwargs)
        elif fmt == "Parquet":
            # PyArrow akzeptiert das compression_level Argument direkt flach
            if level is not None and engine == "pyarrow":
                kwargs["compression_level"] = level

            df.to_parquet(
                fname, engine=engine, compression=codec, **kwargs
            )

        write_time = time.time() - start
        size_mb = os.path.getsize(fname) / (1024**2)

        # --- LESEN ---
        start = time.time()
        if fmt.startswith("CSV"):
            _ = pd.read_csv(fname, compression=kwargs.get("compression", None))
        elif fmt == "Parquet":
            _ = pd.read_parquet(fname, engine=engine)

        read_time = time.time() - start

        # Ergebnisse speichern
        results.append(
            {
                "Format": fmt,
                "Engine": engine if engine else "-",
                "Codec": codec if codec else "-",
                "Level": level if level else "Standard",
                "Größe_MB": round(size_mb, 2),
                "Schreibzeit_s": round(write_time, 2),
                "Lesezeit_s": round(read_time, 2),
            }
        )

    except Exception as e:
        print(f"Fehler bei Kombination {fmt}-{engine}-{codec}: {e}")

    finally:
        # Datei in jedem Fall aufräumen, damit die Festplatte nicht zumüllt
        if os.path.exists(fname):
            os.remove(fname)

# DataFrame erstellen
df_results = pd.DataFrame(results)

# Der Eindeutigkeits-Fix für Ihre Diagramme (keine zusammengefassten Balken mehr!)
df_results["Variante"] = df_results.apply(
    lambda r: f"{r['Format']} ({r['Engine']}) - {r['Codec']} [{r['Level']}]"
    if r["Codec"] != "-"
    else f"{r['Format']} [{r['Level']}]",
    axis=1,
)

import numpy as np
import matplotlib.pyplot as plt
import seaborn as sns

metrics = ["Größe_MB", "Schreibzeit_s", "Lesezeit_s"]

for metric in metrics:
    fig, ax = plt.subplots(figsize=(10, 6), constrained_layout=True)
    sns.barplot(
        data=df_results,
        x=metric,
        y="Variante",
        hue="Engine",
        palette="viridis",
        ax=ax,
    )
    ax.set_title(f"{metric} – Seaborn", fontsize=16)
    ax.set_xlabel(metric)
    ax.set_ylabel("Variante")

    # Maximalen Wert ermitteln, um den Textabstand dynamisch zu berechnen
    max_value = df_results[metric].max()
    # 1% des Maximalwerts als sauberer, skalenunabhängiger Abstand nach dem Balken
    padding = max_value * 0.01

    # Werte an die echten Balken schreiben
    for p in ax.patches:
        width = p.get_width()

        # NUR beschriften, wenn der Balken existiert, nicht NaN ist und größer als 0 ist
        if width > 0 and not np.isnan(width):
            # Berechnet die vertikale Mitte des aktuellen Balkens
            y_pos = p.get_y() + p.get_height() / 2

            ax.text(
                width + padding,
                y_pos,
                f"{width:.2f}",
                va="center",
                ha="left",  # Richtet den Text linksbündig an der berechneten Position aus
                fontsize=9,
            )

    # Legende außerhalb platzieren
    ax.legend(title="Engine", bbox_to_anchor=(1.05, 1), loc="upper left")
    plt.show()

Abschließende Evaluierung und Handlungsempfehlung¶

Die Durchführung des Benchmarks liefert eindeutige algorithmische Messwerte bezüglich Dateigröße, Schreibgeschwindigkeit und Lesezeit. Basierend auf diesen Daten lassen sich differenzierte Kriterien für die Wahl des optimalen Speicherformats ableiten.

Automatische Gesamtbewertung¶

Die kleinste Datei erzeugt die Variante Parquet (fastparquet) - brotli [Standard] mit einer Größe von 26.91 MB.

Die schnellste Schreibzeit erreicht Parquet (pyarrow) - snappy [Standard] mit 2.85 Sekunden.

Die schnellste Lesezeit erreicht Parquet (pyarrow) - zstd [10] mit 0.40 Sekunden.

Die gesamte Verarbeitung aus Schreiben und Lesen dauert bei der kleinsten Datei 1319.82 Sekunden.

Die Rolle klassischer Text- und Archivierungsformate (CSV, ZIP, BZ2)¶

Klassische textbasierte Formate bieten den fundamentalen Vorteil der universellen Lesbarkeit, weisen jedoch je nach Kompression deutliche Performance-Unterschiede auf:

  • Standard-CSV ist die unkomprimierte CSV-Datei und der absolute Spitzenreiter. Der kritische Nachteil liegt jedoch im massiven Speicherbedarf von 736.48 MB. Die Schreibzeit beträgt 27.17 Sekunden, die Lesezeit 13.16 Sekunden.
  • CSV_ZIP: Die Kompression via ZIP bietet einen soliden Mittelweg. Sie reduziert die Dateigröße effizient auf 101.77 MB bei moderaten Verarbeitungszeiten (Schreiben: 41.70 Sekunden und Lesen: 13.75 Sekunden).
  • CSV_BZ2 (Bzip2): Dieses Format erzielt mit 65.79 MB eine der stärksten Kompressionen im Testfeld. In der hier getesteten Standardkonfiguration von Pandas (maximale Kompressionsstufe 9) führt dies jedoch zu einer extrem hohen CPU-Last, was sich in einer Schreibzeit von 90.78 Sekunden und einer Lesezeit von 27.37 Sekunden widerspiegelt.
    • Hinweis zur Systemarchitektur: In reinen Pandas-Umgebungen bremst BZ2 den Workflow aus. In großen Big-Data-Infrastrukturen (wie Apache Spark oder Hadoop) ist BZ2 jedoch hochgradig relevant, da das Format im Gegensatz zu vielen anderen Codecs vollständig splittbar ist. Große Datenmengen können somit trotz Kompression auf Cluster-Ebene parallel von vielen Knoten gleichzeitig verarbeitet werden. Zudem könnte die Schreibzeit durch eine manuelle Herabsetzung der internen Kompressionsstufe bei Bedarf optimiert werden.

Der Technologiewechsel bei Binärformaten: PyArrow als Standard¶

Sobald das Projekt den Bereich der klassischen Textdateien verlässt und auf das spaltenorientierte Parquet-Format setzt, zeigt sich eine deutliche technologische Überlegenheit der PyArrow-Engine gegenüber fastparquet:

  • Status von fastparquet: Die Engine fastparquet gilt im modernen Data-Science-Ökosystem (spätestens mit der Einführung von Pandas 3.0 und der Standardisierung auf das Apache-Arrow-Backend) als weitgehend veraltet (deprecated).
  • Direkter Performance-Vergleich: Bei identischen Rahmenbedingungen (im Standard-Snappy-Verfahren) übertrifft PyArrow die fastparquet-Engine in allen Metriken deutlich:
    • Dateigröße: PyArrow komprimiert effizienter (127.21 MB vs. 159.71 MB).
    • Schreibzeit: PyArrow arbeitet mehr als doppelt so schnell (2.85 Sekunden vs. 6.13 Sekunden).
    • Lesezeit: PyArrow operiert im Millisekundenbereich (0.47 Sekunden), während fastparquet mit 3.18 Sekunden den Leseprozess spürbar verlangsamt.

Kritische Relevanz von Codecs und Kompressionsstufen (Levels)¶

Die Analyse zeigt, dass eine Erhöhung der Kompressionsstufen ab einem bestimmten Punkt in keinem Verhältnis mehr zur gewonnenen Speicherplatzersparnis steht:

  • Das Brotli-Effizienzproblem: Der Codec brotli zeigt bei Erhöhung von Level 10 auf Level 11 eine dramatische Ineffizienz unter PyArrow. Während sich die Dateigröße kaum spürbar verändert (44.52 MB zu 44.07 MB), explodiert die Schreibzeit von 135.78 Sekunden auf 476.22 Sekunden (eine Erhöhung um ca. 340.44 Sekunden).
  • Bei der fastparquet-Implementierung von Brotli bricht das System sogar bei Parquet (fastparquet) - brotli [Standard] mit 1316.48 Sekunden komplett ein.
  • Nach dem Ausschluss von brotli verbleiben für den praktischen Einsatz bei Parquet-Dateien zwei hocheffiziente Codecs unter PyArrow: zstd und snappy. Die Wahl ist vom jeweiligen Anwendungsfall (lokal, Server, Framework-Versionen) abhängig.

Parquet (pyarrow) - zstd [3]¶

  • Größe: 56.45 MB
  • Schreibzeit: 3.18 Sekunden
  • Lesezeit: 0.43 Sekunden
  • Der Speicherplatz-Gewinner: Exzellente Balance. Extrem kleine Datei bei rasanten Lesezeiten.

Parquet (pyarrow) - snappy [Standard]¶

  • Größe: 127.21 MB
  • Schreibzeit: 2.85 Sekunden
  • Lesezeit: 0.47 Sekunden
  • Der Kompatibilitäts-Gewinner: Schnell beim Schreiben, universell unterstützt.

Erkenntnis: Höhere Levels erzwingen rechenintensive Suchalgorithmen, die im Data-Engineering-Alltag immense zeitliche Ressourcen verschwenden.

Abwägung und finale Entscheidungshilfe¶

Für die finale Formatwahl im Projekt wird eine zweistufige Entscheidungsmatrix empfohlen:

  1. Einsatz klassischer Formate: Sofern eine direkte menschliche Lesbarkeit oder die native Weiterverarbeitung in Standard-Bürosoftware (wie Microsoft Excel) zwingend erforderlich ist, bleibt das Standard-CSV-Format für schnelle Zwischenschritte oder die CSV-ZIP-Variante für speicherschonende Archivierung die primäre Wahl.

  2. Einsatz von Spezialformaten (Parquet): Falls für spezielle datentechnische Zwecke nicht mit klassischen Textformaten gearbeitet wird und die Datenanalysen auf maximalen Durchsatz optimiert werden sollen, ist der Einsatz von Parquet unter der PyArrow-Engine zwingend angeraten. Innerhalb dieses Ökosystems existieren zwei Optionen:

    • Der technische Favorit (ZSTD): Aus reiner Performance-Sicht bietet ZSTD (z. B. auf Level 3) die beste Balance. Es reduziert den Speicherbedarf im Vergleich zu Snappy um mehr als die Hälfte (56.45 MB), hält die Lesezeit bei rasanten 0.43 Sekunden und wird von modernen Frameworks (Polars, DuckDB, moderne Pandas-Versionen) nativ unterstützt.
    • Die kompatible Projekt-Empfehlung (Snappy): Trotz des höheren Speicherbedarfs (127.21 MB) wird für das vorliegende Projekt die Verwendung von Snappy (Standard) präferiert. Der Grund hierfür liegt in der maximalen Abwärtskompatibilität. Ältere Cloud-Infrastrukturen, Legacy-Hadoop-Systeme oder ältere Server-Bibliotheken setzen Snappy oft zwingend voraus oder nutzen es als festen Standard-Codec.

Fazit: Wenn Speicherplatz auf Systemen die primäre Engstelle darstellt, ist der Wechsel auf pyarrow mit zstd (Level 3) dringend empfohlen. Steht jedoch die reibungslose, fehlerfreie Integration in bestehende, potenziell ältere Pipelines und gemischte Framework-Umgebungen im Vordergrund, bleibt pyarrow mit snappy der sicherste und kompatibelste Standard für dieses Projekt.
